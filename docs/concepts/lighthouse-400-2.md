## 2. Accessibility (접근성) — "누구나 쓸 수 있는가?"

"접근성이 왜 중요해요? 시각 장애인분들이 제 블로그를 보나요?"

솔직히 말하면, **구글이 점수에 반영하니까 중요합니다.**\
구글은 접근성 높은 사이트를 좋아합니다. 높을수록 상위 노출이 잘 됩니다.

### 2-1. 공식 점검 항목

공식 문서가 안내하는 Accessibility 항목들:

| 분류 | 체크 항목 | 쉬운 뜻 |
|---|---|---|
| **ARIA** | ARIA 역할(role) 적용 | 화면 읽어주는 프로그램이 이해할 수 있는 구조 |
| **키보드** | 키보드 네비게이션 | 마우스 없이 키보드만으로 모든 기능 사용 가능 |
| **포커스** | 포커스 관리 | 탭 키로 이동 시 시각적으로 보임 |
| **이미지** | alt 텍스트 | 이미지에 "이 그림이 뭔지" 설명 |
| **색상** | 색상 대비 4.5:1 이상 | 글씨가 배경과 충분히 구분 |
| **폼** | 라벨 연결 | input마다 label 명확히 연결 |
| **언어** | `<html lang>` 명시 | 페이지 언어 명시 (예: `ko`) |
| **헤딩** | 헤딩 계층 순서 | H1 → H2 → H3 순서 준수 |

### 2-2. 색상 대비 비율 — 가장 흔한 감점

WCAG 2.1 AA 기준:

| 텍스트 종류 | 최소 대비 비율 |
|---|---|
| 일반 텍스트 (18px 미만) | 4.5:1 |
| 큰 텍스트 (18px 이상, 14px Bold 이상) | 3:1 |
| 비텍스트 요소 (아이콘 등) | 3:1 |

```
예시:
─────────────
배경: 흰색 (#FFFFFF)
글씨: 연한 회색 (#CCCCCC) → 대비 1.6:1 ❌ 불합격
글씨: 진한 회색 (#666666) → 대비 5.7:1 ✅ 합격
```

> 💡 **우리 템플릿의 기본 색상은 4.5:1 이상으로 설정**되어 있습니다.\
> 색상 커스텀 시 주의: 너무 옅은 색은 피하세요.

## 3. Best Practices (모범 사례) — "웹 표준을 지키는가?"

인터넷에는 "이렇게 만들어야 한다"는 기준이 있습니다.\
이걸 지키는지 체크합니다.

### 3-1. 공식 점검 항목

| 분류 | 체크 항목 | 우리 상태 |
|---|---|---|
| **보안** | HTTPS 사용 | ✅ Vercel 자동 |
| **보안** | 안전한 쿠키 (Secure, HttpOnly) | ✅ 템플릿 기본 |
| **보안** | CSP (Content Security Policy) | ✅ 설정됨 |
| **콘솔** | 콘솔 에러 없음 | ✅ 템플릿 깨끗 |
| **HTML** | doctype 선언 | ✅ Next.js 자동 |
| **HTML** | charset 명시 (UTF-8) | ✅ Next.js 자동 |
| **이미지** | 적절한 종횡비 (왜곡 없음) | ✅ 자동 처리 |
| **이미지** | 적절한 해상도 | ✅ 자동 최적화 |
| **JavaScript** | 사용 중단된 API 미사용 | ✅ 최신 라이브러리 |
| **JavaScript** | 소스맵 미공개 (프로덕션) | ✅ Next.js 자동 |

### 3-2. HTTPS — 왜 중요한가?

- **2018년부터** 구글은 HTTPS가 아닌 사이트에 "안전하지 않음" 경고 표시
- HTTPS 사이트가 HTTP 사이트보다 **상위 노출**됨 (공식 발표)
- 사용자 신뢰도 ↑ (자물쇠 🔒 아이콘)

> 💡 Vercel은 무료로 자동 HTTPS 인증서를 발급합니다 (Let's Encrypt).\
> 여러분이 따로 할 일 없음.

## 4. SEO — "구글이 잘 읽을 수 있는가?"

구글 봇이 사이트를 방문했을 때, 내용을 잘 이해할 수 있는지 체크합니다.

### 4-1. 공식 점검 항목

| 분류 | 체크 항목 | 쉬운 뜻 | 우리 상태 |
|---|---|---|---|
| **메타** | `<title>` 존재 | 페이지 제목 | ✅ 자동 생성 |
| **메타** | `<meta description>` | 검색 결과 설명 | ✅ 자동 생성 |
| **모바일** | viewport 메타 태그 | 모바일 대응 | ✅ Next.js 자동 |
| **콘텐츠** | 텍스트 폰트 크기 12px+ | 모바일에서 읽기 쉬움 | ✅ 기본 16px |
| **링크** | 모든 링크에 텍스트 | "여기 클릭" 같은 모호한 링크 X | ⚠️ 글쓸 때 주의 |
| **링크** | rel="canonical" | 중복 콘텐츠 방지 | ✅ 자동 |
| **크롤** | robots.txt 유효성 | 크롤 차단 안 됨 | ✅ 자동 |
| **인덱스** | noindex 태그 없음 | 검색에서 제외 안 됨 | ✅ 기본 false |
| **이미지** | alt 속성 | 이미지 대체 텍스트 | ⚠️ 글쓸 때 주의 |
| **구조** | 구조화 데이터 유효 | Schema.org 마크업 | ✅ 자동 |

### 4-2. ⚠️ 글쓸 때 주의해야 할 항목

대부분 자동이지만, **이 2가지는 글 쓸 때 본인이 챙겨야** 합니다:

#### (1) 링크 텍스트
```
❌ 나쁜 예: "자세히 보기" / "여기 클릭"
✅ 좋은 예: "맥북 에어 M3 발열 해결법"
```

#### (2) 이미지 alt 텍스트
```
❌ 나쁜 예: alt="" (비어있음) / alt="이미지1"
✅ 좋은 예: alt="맥북 에어 M3의 발열 상태 — Core Temp 측정 화면"
```

> 💡 **글쓰기 강의에서** 이 부분을 다시 강조합니다.\
> AI에게 글을 시킬 때도 "alt 텍스트 챙겨줘"라고 하면 됩니다.

## 5. 400점 vs 250점 — 실제로 얼마나 차이 나나요?

**같은 내용의 글**을 올렸을 때:

| | 250점 사이트 | 400점 사이트 |
|---|---|---|
| 구글에 뜨는 속도 | 3~7일 걸림 | **24시간 이내** |
| 평균 검색 순위 | 15~30위 (2~3페이지) | **3~10위 (1페이지!)** |
| 클릭률 | 1~3% | **5~15%** |
| 월 트래픽 | 500명 | **5,000명** |

> 🔥 **같은 글, 같은 노력인데 10배 차이.**\
> 차이를 만드는 건 **테크니컬 SEO** 점수입니다.\
> 그리고 이걸 **설치만으로 해결하는 게** 이 강의의 핵심입니다.

구글 검색 1페이지에 나오는 것과 2페이지에 나오는 것은 하늘과 땅 차이입니다.\
대부분의 사람들은 **1페이지만 보고 끝**이에요. 2페이지는 거의 안 봅니다.

### 5-1. 검색 결과 페이지별 클릭률 (실제 데이터)

| 순위 | 평균 클릭률 |
|---|---|
| 1위 | 27.6% |
| 2위 | 15.8% |
| 3위 | 11.0% |
| 4위 | 8.4% |
| 5위 | 6.3% |
| 6~10위 | 2~5% |
| 11~20위 (2페이지) | < 1% |
| 21위~ (3페이지~) | 거의 0% |

— Backlinko 2023 연구 (수십억 검색 결과 분석)

> 💡 **1페이지 진입이 전부**입니다. Lighthouse 400점은 그걸 가능하게 합니다.

## 6. 직접 측정해보기

여러분도 아무 사이트의 Lighthouse 점수를 측정할 수 있습니다!

### 방법 1: Chrome DevTools (가장 정확)

1. **크롬(Chrome)** 브라우저를 엽니다
2. 측정하고 싶은 사이트에 들어갑니다
3. 키보드에서 **F12** 키를 누릅니다 (Mac은 `Cmd + Option + I`)
4. 위쪽 탭에서 **"Lighthouse"**를 클릭합니다
5. **"Categories"**: Performance, Accessibility, Best Practices, SEO 체크
6. **"Device"**: Mobile 또는 Desktop 선택 (모바일 권장)
7. **"Analyze page load"** 버튼을 클릭합니다
8. 30초~1분 기다리면 점수가 나옵니다!

### 방법 2: PageSpeed Insights (가장 쉬움)

웹사이트 주소만 넣으면 자동으로 측정해줍니다:

| 도구 | 주소 | 특징 |
|------|------|------|
| **PageSpeed Insights** | [pagespeed.web.dev](https://pagespeed.web.dev) | 구글 공식. **Field 데이터까지** 보여줌 |
| **web.dev/measure** | [web.dev/measure](https://web.dev/measure) | 구글 공식. 더 자세한 분석 |

### 방법 3: 명령줄 (개발자용)

```bash
npm install -g lighthouse
lighthouse https://myblog.com --view
```

자동으로 HTML 보고서를 열어줍니다.

### 한번 해보세요!

1. [pagespeed.web.dev](https://pagespeed.web.dev)에 접속합니다
2. 네이버 블로그 주소를 하나 넣어보세요 → 모바일 점수 50~70점
3. 그다음 [coleitai-main.vercel.app](https://coleitai-main.vercel.app)를 넣어보세요 → 90+
4. **점수 차이를 눈으로 확인하면** "아, 이래서 400점이 중요하구나" 체감이 됩니다!

## 7. Lighthouse 보고서 읽는 법

PageSpeed Insights 결과를 받으면 어떻게 봐야 하나?

### 7-1. 보고서 구조

```
┌─────────────────────────────────────────┐
│  ① 종합 점수 (4개 카테고리)              │
│  ② Core Web Vitals 평가 (Field)         │
│  ③ Lab 데이터 (5개 지표)                │
│  ④ 진단 (Diagnostics)                   │
│  ⑤ 통과한 감사 (Passed Audits)          │
│  ⑥ 적용 가능한 기회 (Opportunities)     │
└─────────────────────────────────────────┘
```

### 7-2. 우선순위 — 어디부터 봐야 하나?

1. **⑥ Opportunities (기회)** 먼저
   - 가장 큰 효과 있는 개선 사항 제시
   - "이미지 최적화", "사용하지 않는 JS 제거" 등
   - 예상 절약 시간(초 단위) 표시
2. **④ Diagnostics (진단)** 그다음
   - 직접 점수는 아니지만 참고할 정보
3. **③ Lab 데이터** 마지막
   - 어떤 지표가 빨강(나쁨)인지 확인

> 💡 우리 템플릿을 쓰면 **Opportunities가 거의 비어있습니다.**\
> 이미 다 적용되어 있어서요.

## 8. 확장 기능 — Lighthouse Plugins

공식 문서에 따르면 Lighthouse는 **플러그인 시스템**을 지원합니다:

- 특정 영역 전문가들이 추가 감사 모듈 작성 가능
- 새 카테고리로 보고서에 통합됨
- 예: SEO 전문 플러그인, 개인정보 보호 플러그인

또한 **Stack Packs**라는 기능으로:
- 사이트가 사용 중인 기술(WordPress, Next.js, React 등) 자동 감지
- 해당 기술에 특화된 권장 사항 제공

> 💡 Next.js 사이트인 우리 템플릿엔 Next.js 전용 Stack Pack 권장 사항이 자동 적용됩니다.

## 9. Lighthouse CI — 자동 회귀 방지

공식 문서가 소개하는 **Lighthouse CI**:

> "Lighthouse CI는 사이트 변경 사항이 성능 저하를 일으키지 않도록 회귀 방지를 가능하게 합니다."

이게 무슨 뜻이냐면:
- 새 코드를 push할 때마다 자동으로 Lighthouse 측정
- 점수가 떨어지면 → 빌드 실패 + 알림
- 즉, **실수로 점수 떨어지는 코드를 못 올리게 막아줍니다**

> 💡 본 강의에서는 다루지 않지만, 사이트가 커지면 도입 가치 있음.
