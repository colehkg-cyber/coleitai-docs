# Lighthouse 400점 해부

> 구글 봇이 가장 좋아하는 완벽한 구조. 이걸 우리는 0원으로 달성합니다.\
> — 본 문서는 [Chrome 공식 Lighthouse 문서](https://developer.chrome.com/docs/lighthouse/overview?hl=ko)를 바탕으로 작성되었습니다.

---

## 0. Lighthouse란? (공식 정의)

**Lighthouse는 구글이 직접 만든, 웹 페이지 품질을 측정하고 개선하기 위한 오픈소스 자동화 도구입니다.**

> "Lighthouse는 웹 페이지의 품질을 개선하는 데 도움이 되는 도구입니다. 공개 사이트와 인증이 필요한 사이트 모두에 실행할 수 있으며, URL을 제공받으면 페이지에 대해 일련의 감사(audit)를 수행하고 보고서를 생성합니다." — Chrome Developers 공식 문서

쉽게 말하면, 사이트의 **성적표**예요.\
5가지 카테고리가 있고, 각각 100점 만점입니다.\
이 중 본 강의에서 집중하는 **4개**를 합치면 **400점 만점.**

```
┌────────────────────────────────────────────┐
│            LIGHTHOUSE SCORE                │
│                                            │
│  Performance ████████████████████ 100      │
│  (성능 - 사이트가 빠른가?)                  │
│                                            │
│  Accessibility ████████████████████ 100    │
│  (접근성 - 누구나 사용할 수 있는가?)        │
│                                            │
│  Best Practices ████████████████████ 100   │
│  (모범사례 - 웹 표준을 지키는가?)           │
│                                            │
│  SEO ████████████████████ 100              │
│  (검색최적화 - 구글이 잘 읽을 수 있는가?)   │
│                                            │
│  TOTAL: 400 / 400  ✅                      │
└────────────────────────────────────────────┘
```

> 💡 400점에 가까울수록 구글이 좋아합니다.\
> 구글이 좋아하면? **검색 결과 상위에 노출됩니다.**

### Lighthouse가 측정하는 5개 카테고리 (공식)

공식 문서에 따르면 Lighthouse는 다음 5가지를 평가합니다:

| # | 카테고리 | 한국어 | 본 강의 |
|---|---|---|---|
| 1 | Performance | 성능 | ✅ 핵심 |
| 2 | Accessibility | 접근성 | ✅ 핵심 |
| 3 | Best Practices | 모범 사례 | ✅ 핵심 |
| 4 | SEO | 검색 최적화 | ✅ 핵심 |
| 5 | Agentic Browsing | 에이전트 브라우징 | (선택, 신규) |

> 💡 본 강의에서는 가장 중요한 1~4번 (400점)에 집중합니다.\
> 5번은 AI 에이전트가 페이지를 자동으로 탐색할 때의 호환성 측정 (신규 기능).

### Lighthouse를 실행하는 5가지 공식 방법

공식 문서가 안내하는 실행 방법:

1. **Chrome DevTools** — Chrome 브라우저에 내장 (가장 추천, 인증 페이지도 가능)
2. **Command Line** — `npm install -g lighthouse` 후 `lighthouse <url>`
3. **Node Module** — CI/CD 파이프라인에 통합
4. **PageSpeed Insights** — 웹 페이지에서 URL만 입력 ([pagespeed.web.dev](https://pagespeed.web.dev))
5. **Chrome Extension** — 빠른 측정용 확장 프로그램

> 💡 우리는 주로 **PageSpeed Insights** (웹)와 **Chrome DevTools** (브라우저 내장)를 씁니다.

## 1. Performance (성능) — "이 사이트, 빠른가?"

사이트가 느리면 방문자가 떠납니다.\
구글은 빠른 사이트를 좋아합니다. 이게 **가장 중요한** 항목이에요.

### 1-1. 5개 핵심 지표 + 공식 가중치

공식 문서(Lighthouse 10 기준)에 명시된 **각 지표의 가중치**:

| 지표 | 풀네임 | 가중치 | 합격 기준 | 쉬운 뜻 |
|---|---|---|---|---|
| **FCP** | First Contentful Paint | 10% | 1.8초 이하 | 화면에 뭔가 처음 보이는 시간 |
| **SI** | Speed Index | 10% | 3.4초 이하 | 전체적으로 얼마나 빠르게 느껴지는지 |
| **LCP** | Largest Contentful Paint | 25% | 2.5초 이하 | 가장 큰 내용이 뜨는 시간 |
| **TBT** | Total Blocking Time | 30% | 0.2초 이하 | 화면이 멈추는(버벅이는) 시간 |
| **CLS** | Cumulative Layout Shift | 25% | 0.1 이하 | 화면이 갑자기 움직이는 정도 |

> 💡 **가장 중요한 지표는 TBT (30%)와 LCP (25%) + CLS (25%)** — 총 80%.\
> 이 3개만 잡아도 Performance 90+ 가능.

### 1-2. 점수 산정 방식 (공식)

공식 문서에 따르면 Lighthouse Performance 점수는:

1. 각 지표를 **0~100점 척도**로 변환
   - **로그 정규 분포(log-normal distribution)** 사용
   - HTTP Archive의 실제 웹 성능 데이터 기반
   - 25th percentile → 50점, 8th percentile → 90점
2. 가중치를 곱해서 **가중 평균** 계산
3. 최종 0~100 점수 산출

### 1-3. 점수 임계값 (공식)

공식 색상 코딩:

| 점수 | 색상 | 등급 | 의미 |
|---|---|---|---|
| 0~49 | 🔴 빨강 | Poor (나쁨) | 즉각 개선 필요 |
| 50~89 | 🟠 주황 | Needs Improvement (개선 필요) | 부족함 |
| 90~100 | 🟢 초록 | Good (양호) | 만족스러운 사용자 경험 |

> 💡 공식 문서: "만족스러운 사용자 경험을 위해서는 **90~100점 범위**가 필요합니다."

### 1-4. 점수 곡선의 비선형성

공식 문서가 강조하는 중요한 사실:

> "로그 정규 분포를 따르기 때문에, **이미 높은 점수를 더 높이려면 지수적으로 많은 노력이 필요**합니다.\
> 예를 들어, 95점에서 100점으로 가는 데는 90점에서 94점으로 가는 것과 거의 동등한 노력이 필요합니다."

이게 왜 중요하냐면:

- **0 → 50점**: 비교적 쉬움 (큰 문제 1~2개 해결)
- **50 → 90점**: 중간 (디테일한 최적화)
- **90 → 100점**: 매우 어려움 (수십 가지 미세 조정)

> 💡 **90점만 넘어도 충분히 빠른 사이트**입니다.\
> 100점 강박은 버리세요. 90+로도 구글이 충분히 좋아합니다.

### 1-5. 우리 템플릿이 100점을 만드는 방법

| 최적화 기법 | 효과 | 지표 |
|---|---|---|
| **SSG (정적 사이트 생성)** | 미리 만들어둔 HTML 제공 | FCP, LCP ↑ |
| **이미지 자동 최적화** (WebP/AVIF) | 용량 50~80% 감소 | LCP, SI ↑ |
| **코드 스플리팅** | 필요한 부분만 로드 | TBT ↓ |
| **이미지 크기 명시** | 레이아웃 안정화 | CLS ↓ |
| **폰트 preload** | 폰트 지연 로드 방지 | CLS ↓ |
| **JavaScript 최소화** | 메인 스레드 점유 시간 ↓ | TBT ↓ |
| **CDN 배포 (Vercel Edge)** | 전 세계 어디서나 빠름 | FCP, LCP ↑ |

### 1-6. Lab 데이터 vs Field 데이터

공식 문서가 강조하는 차이:

| 구분 | Lab 데이터 | Field 데이터 |
|---|---|---|
| **측정** | 통제된 환경 (한 번) | 실제 사용자 (수천~수만 명) |
| **도구** | DevTools Lighthouse | PageSpeed Insights, CrUX |
| **장점** | 빠르고 일관됨 | 실제 사용자 경험 반영 |
| **단점** | 실제 사용자와 다를 수 있음 | 데이터 수집 시간 필요 |

> 💡 구글은 **Field 데이터(실제 사용자 경험)**를 검색 순위에 반영합니다.\
> Lab에서 100점이어도 실제 사용자가 느리게 느꼈으면 감점.

## 2. Accessibility (접근성) — "누구나 쓸 수 있는가?"

"접근성이 왜 중요해요? 시각 장애인분들이 제 블로그를 보나요?"

솔직히 말하면, **구글이 점수에 반영하니까 중요합니다.**\
구글은 접근성 높은 사이트를 좋아합니다. 높을수록 상위 노출이 잘 됩니다.

### 2-1. 공식 점검 항목

공식 문서가 안내하는 Accessibility 항목들:

| 분류 | 체크 항목 | 쉬운 뜻 |
|---|---|---|
| **ARIA** | ARIA 역할(role) 적용 | 화면 읽어주는 프로그램이 이해할 수 있는 구조 |
| **키보드** | 키보드 네비게이션 | 마우스 없이 키보드만으로 모든 기능 사용 가능 |
| **포커스** | 포커스 관리 | 탭 키로 이동 시 시각적으로 보임 |
| **이미지** | alt 텍스트 | 이미지에 "이 그림이 뭔지" 설명 |
| **색상** | 색상 대비 4.5:1 이상 | 글씨가 배경과 충분히 구분 |
| **폼** | 라벨 연결 | input마다 label 명확히 연결 |
| **언어** | `<html lang>` 명시 | 페이지 언어 명시 (예: `ko`) |
| **헤딩** | 헤딩 계층 순서 | H1 → H2 → H3 순서 준수 |

### 2-2. 색상 대비 비율 — 가장 흔한 감점

WCAG 2.1 AA 기준:

| 텍스트 종류 | 최소 대비 비율 |
|---|---|
| 일반 텍스트 (18px 미만) | 4.5:1 |
| 큰 텍스트 (18px 이상, 14px Bold 이상) | 3:1 |
| 비텍스트 요소 (아이콘 등) | 3:1 |

```
예시:
─────────────
배경: 흰색 (#FFFFFF)
글씨: 연한 회색 (#CCCCCC) → 대비 1.6:1 ❌ 불합격
글씨: 진한 회색 (#666666) → 대비 5.7:1 ✅ 합격
```

> 💡 **우리 템플릿의 기본 색상은 4.5:1 이상으로 설정**되어 있습니다.\
> 색상 커스텀 시 주의: 너무 옅은 색은 피하세요.

## 3. Best Practices (모범 사례) — "웹 표준을 지키는가?"

인터넷에는 "이렇게 만들어야 한다"는 기준이 있습니다.\
이걸 지키는지 체크합니다.

### 3-1. 공식 점검 항목

| 분류 | 체크 항목 | 우리 상태 |
|---|---|---|
| **보안** | HTTPS 사용 | ✅ Vercel 자동 |
| **보안** | 안전한 쿠키 (Secure, HttpOnly) | ✅ 템플릿 기본 |
| **보안** | CSP (Content Security Policy) | ✅ 설정됨 |
| **콘솔** | 콘솔 에러 없음 | ✅ 템플릿 깨끗 |
| **HTML** | doctype 선언 | ✅ Next.js 자동 |
| **HTML** | charset 명시 (UTF-8) | ✅ Next.js 자동 |
| **이미지** | 적절한 종횡비 (왜곡 없음) | ✅ 자동 처리 |
| **이미지** | 적절한 해상도 | ✅ 자동 최적화 |
| **JavaScript** | 사용 중단된 API 미사용 | ✅ 최신 라이브러리 |
| **JavaScript** | 소스맵 미공개 (프로덕션) | ✅ Next.js 자동 |

### 3-2. HTTPS — 왜 중요한가?

- **2018년부터** 구글은 HTTPS가 아닌 사이트에 "안전하지 않음" 경고 표시
- HTTPS 사이트가 HTTP 사이트보다 **상위 노출**됨 (공식 발표)
- 사용자 신뢰도 ↑ (자물쇠 🔒 아이콘)

> 💡 Vercel은 무료로 자동 HTTPS 인증서를 발급합니다 (Let's Encrypt).\
> 여러분이 따로 할 일 없음.

## 4. SEO — "구글이 잘 읽을 수 있는가?"

구글 봇이 사이트를 방문했을 때, 내용을 잘 이해할 수 있는지 체크합니다.

### 4-1. 공식 점검 항목

| 분류 | 체크 항목 | 쉬운 뜻 | 우리 상태 |
|---|---|---|---|
| **메타** | `<title>` 존재 | 페이지 제목 | ✅ 자동 생성 |
| **메타** | `<meta description>` | 검색 결과 설명 | ✅ 자동 생성 |
| **모바일** | viewport 메타 태그 | 모바일 대응 | ✅ Next.js 자동 |
| **콘텐츠** | 텍스트 폰트 크기 12px+ | 모바일에서 읽기 쉬움 | ✅ 기본 16px |
| **링크** | 모든 링크에 텍스트 | "여기 클릭" 같은 모호한 링크 X | ⚠️ 글쓸 때 주의 |
| **링크** | rel="canonical" | 중복 콘텐츠 방지 | ✅ 자동 |
| **크롤** | robots.txt 유효성 | 크롤 차단 안 됨 | ✅ 자동 |
| **인덱스** | noindex 태그 없음 | 검색에서 제외 안 됨 | ✅ 기본 false |
| **이미지** | alt 속성 | 이미지 대체 텍스트 | ⚠️ 글쓸 때 주의 |
| **구조** | 구조화 데이터 유효 | Schema.org 마크업 | ✅ 자동 |

### 4-2. ⚠️ 글쓸 때 주의해야 할 항목

대부분 자동이지만, **이 2가지는 글 쓸 때 본인이 챙겨야** 합니다:

#### (1) 링크 텍스트
```
❌ 나쁜 예: "자세히 보기" / "여기 클릭"
✅ 좋은 예: "맥북 에어 M3 발열 해결법"
```

#### (2) 이미지 alt 텍스트
```
❌ 나쁜 예: alt="" (비어있음) / alt="이미지1"
✅ 좋은 예: alt="맥북 에어 M3의 발열 상태 — Core Temp 측정 화면"
```

> 💡 **글쓰기 강의에서** 이 부분을 다시 강조합니다.\
> AI에게 글을 시킬 때도 "alt 텍스트 챙겨줘"라고 하면 됩니다.

## 5. 400점 vs 250점 — 실제로 얼마나 차이 나나요?

**같은 내용의 글**을 올렸을 때:

| | 250점 사이트 | 400점 사이트 |
|---|---|---|
| 구글에 뜨는 속도 | 3~7일 걸림 | **24시간 이내** |
| 평균 검색 순위 | 15~30위 (2~3페이지) | **3~10위 (1페이지!)** |
| 클릭률 | 1~3% | **5~15%** |
| 월 트래픽 | 500명 | **5,000명** |

> 🔥 **같은 글, 같은 노력인데 10배 차이.**\
> 차이를 만드는 건 **테크니컬 SEO** 점수입니다.\
> 그리고 이걸 **설치만으로 해결하는 게** 이 강의의 핵심입니다.

구글 검색 1페이지에 나오는 것과 2페이지에 나오는 것은 하늘과 땅 차이입니다.\
대부분의 사람들은 **1페이지만 보고 끝**이에요. 2페이지는 거의 안 봅니다.

### 5-1. 검색 결과 페이지별 클릭률 (실제 데이터)

| 순위 | 평균 클릭률 |
|---|---|
| 1위 | 27.6% |
| 2위 | 15.8% |
| 3위 | 11.0% |
| 4위 | 8.4% |
| 5위 | 6.3% |
| 6~10위 | 2~5% |
| 11~20위 (2페이지) | < 1% |
| 21위~ (3페이지~) | 거의 0% |

— Backlinko 2023 연구 (수십억 검색 결과 분석)

> 💡 **1페이지 진입이 전부**입니다. Lighthouse 400점은 그걸 가능하게 합니다.

## 6. 직접 측정해보기

여러분도 아무 사이트의 Lighthouse 점수를 측정할 수 있습니다!

### 방법 1: Chrome DevTools (가장 정확)

1. **크롬(Chrome)** 브라우저를 엽니다
2. 측정하고 싶은 사이트에 들어갑니다
3. 키보드에서 **F12** 키를 누릅니다 (Mac은 `Cmd + Option + I`)
4. 위쪽 탭에서 **"Lighthouse"**를 클릭합니다
5. **"Categories"**: Performance, Accessibility, Best Practices, SEO 체크
6. **"Device"**: Mobile 또는 Desktop 선택 (모바일 권장)
7. **"Analyze page load"** 버튼을 클릭합니다
8. 30초~1분 기다리면 점수가 나옵니다!

### 방법 2: PageSpeed Insights (가장 쉬움)

웹사이트 주소만 넣으면 자동으로 측정해줍니다:

| 도구 | 주소 | 특징 |
|------|------|------|

## 7. Lighthouse 보고서 읽는 법

PageSpeed Insights 결과를 받으면 어떻게 봐야 하나?

### 7-1. 보고서 구조

```
┌─────────────────────────────────────────┐
│  ① 종합 점수 (4개 카테고리)              │
│  ② Core Web Vitals 평가 (Field)         │
│  ③ Lab 데이터 (5개 지표)                │
│  ④ 진단 (Diagnostics)                   │
│  ⑤ 통과한 감사 (Passed Audits)          │
│  ⑥ 적용 가능한 기회 (Opportunities)     │
└─────────────────────────────────────────┘
```

### 7-2. 우선순위 — 어디부터 봐야 하나?

1. **⑥ Opportunities (기회)** 먼저
   - 가장 큰 효과 있는 개선 사항 제시
   - "이미지 최적화", "사용하지 않는 JS 제거" 등
   - 예상 절약 시간(초 단위) 표시
2. **④ Diagnostics (진단)** 그다음
   - 직접 점수는 아니지만 참고할 정보
3. **③ Lab 데이터** 마지막
   - 어떤 지표가 빨강(나쁨)인지 확인

> 💡 우리 템플릿을 쓰면 **Opportunities가 거의 비어있습니다.**\
> 이미 다 적용되어 있어서요.

## 8. 확장 기능 — Lighthouse Plugins

공식 문서에 따르면 Lighthouse는 **플러그인 시스템**을 지원합니다:

- 특정 영역 전문가들이 추가 감사 모듈 작성 가능
- 새 카테고리로 보고서에 통합됨
- 예: SEO 전문 플러그인, 개인정보 보호 플러그인

또한 **Stack Packs**라는 기능으로:
- 사이트가 사용 중인 기술(WordPress, Next.js, React 등) 자동 감지
- 해당 기술에 특화된 권장 사항 제공

> 💡 Next.js 사이트인 우리 템플릿엔 Next.js 전용 Stack Pack 권장 사항이 자동 적용됩니다.

## 9. Lighthouse CI — 자동 회귀 방지

공식 문서가 소개하는 **Lighthouse CI**:

> "Lighthouse CI는 사이트 변경 사항이 성능 저하를 일으키지 않도록 회귀 방지를 가능하게 합니다."

이게 무슨 뜻이냐면:
- 새 코드를 push할 때마다 자동으로 Lighthouse 측정
- 점수가 떨어지면 → 빌드 실패 + 알림
- 즉, **실수로 점수 떨어지는 코드를 못 올리게 막아줍니다**

> 💡 본 강의에서는 다루지 않지만, 사이트가 커지면 도입 가치 있음.
